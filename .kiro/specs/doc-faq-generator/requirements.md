# Requirements Document

## Introduction

The doc-faq-generator is a Python CLI tool that reads a folder of documents (PDF, DOCX, and TXT files), sends their content to the Anthropic Claude API (claude-sonnet-4-5) in manageable chunks, generates Q&A pairs from each chunk, merges and deduplicates results across all chunks and documents, and saves the final FAQ to `output/faq.md` in Markdown format. The tool is designed to handle large document sets gracefully and securely, loading the API key exclusively from a `.env` file.

## Glossary

- **CLI**: Command-line interface — the tool is invoked from a terminal with arguments
- **Tool**: The doc-faq-generator Python program
- **Document**: A single file with a `.pdf`, `.docx`, or `.txt` extension
- **Folder**: A filesystem directory supplied by the user as input
- **Chunk**: A contiguous slice of text extracted from a Document, sized to fit within the model's context limits
- **FAQ**: Frequently Asked Questions — the merged, deduplicated set of Q&A pairs produced by the Tool
- **QA_Pair**: A single question and its corresponding answer, generated by the Claude model
- **Merger**: The component responsible for combining QA_Pairs from all chunks into a single coherent FAQ
- **Deduplicator**: The component responsible for identifying and removing semantically overlapping questions from the FAQ
- **Claude_API**: The Anthropic Claude API endpoint accessed using the `claude-sonnet-4-5` model
- **API_Key**: The secret credential used to authenticate requests to the Claude_API, loaded from a `.env` file
- **Output_File**: The file at `output/faq.md` where the final FAQ is written

## Requirements

### Requirement 1: CLI Entry Point and Folder Input

**User Story:** As a developer, I want to invoke the tool from the command line with a folder path, so that I can point it at any directory of documents and receive a generated FAQ.

#### Acceptance Criteria

1. THE Tool SHALL accept a folder path as a required positional command-line argument.
2. IF no folder path argument is provided, THEN THE Tool SHALL print a usage message (e.g., `Usage: faq-generator <folder_path>`) and exit with exit code 2.
3. WHEN the provided folder path does not exist, THE Tool SHALL print the message `Error: path '<path>' not found` and exit with exit code 1.
4. WHEN the provided folder path is a file rather than a directory, THE Tool SHALL print the message `Error: '<path>' is not a directory` and exit with exit code 1.
5. WHEN the provided folder path exists but contains no supported Document files, THE Tool SHALL print the message `No supported documents found in '<path>'` and exit with exit code 1.

---

### Requirement 2: Document Discovery and Reading

**User Story:** As a user, I want the tool to automatically find and read all PDF, DOCX, and TXT files in the folder, so that I do not have to specify individual files manually.

#### Acceptance Criteria

1. WHEN the folder path is valid, THE Tool SHALL discover all files with `.pdf`, `.docx`, and `.txt` extensions within the Folder, descending into subdirectories up to a maximum depth of 10 levels.
2. WHEN a `.txt` file is discovered, THE Tool SHALL read its contents as UTF-8 encoded text; the file must be no larger than 100 MB.
3. WHEN a `.pdf` file is discovered, THE Tool SHALL extract the full text content from all pages of the Document; the file must be no larger than 100 MB.
4. WHEN a `.docx` file is discovered, THE Tool SHALL extract the full text content from all paragraphs of the Document; the file must be no larger than 100 MB.
5. IF a `.txt` file cannot be decoded as UTF-8, THEN THE Tool SHALL log a warning identifying the file path and reason (encoding failure), skip that file, and continue processing remaining documents.
6. IF a Document cannot be read due to a file system or parsing error, THEN THE Tool SHALL log a warning identifying the file path and reason for failure, and continue processing remaining documents.
7. IF the total number of discovered files across all supported extensions exceeds 10,000, THEN THE Tool SHALL process only the first 10,000 files in alphabetical order by full path, and log a warning stating the limit was reached.

---

### Requirement 3: API Key Loading

**User Story:** As a developer, I want the API key loaded exclusively from a `.env` file, so that secrets are never hardcoded in source code or exposed on the command line.

#### Acceptance Criteria

1. WHEN the Tool starts up, THE Tool SHALL load the `ANTHROPIC_API_KEY` value from a `.env` file located in the working directory.
2. IF the `.env` file does not exist in the working directory, THEN THE Tool SHALL print `Error: .env file not found in working directory` and exit with a non-zero exit code.
3. IF the `.env` file exists but does not contain an `ANTHROPIC_API_KEY` entry, THEN THE Tool SHALL print `Error: ANTHROPIC_API_KEY not found in .env file` and exit with a non-zero exit code.
4. IF the `ANTHROPIC_API_KEY` entry in the `.env` file is present but its value is an empty string, THEN THE Tool SHALL print `Error: ANTHROPIC_API_KEY is empty` and exit with a non-zero exit code.
5. THE Tool SHALL never accept the API key as a command-line argument, and SHALL not read it from environment variables set outside the `.env` file.

---

### Requirement 4: Text Chunking

**User Story:** As a developer, I want large documents split into chunks before being sent to the model, so that token limits are respected and all content is processed.

#### Acceptance Criteria

1. THE Tool SHALL split each Document's extracted text into Chunks of at most 3,000 words, where a word is defined as a whitespace-delimited token.
2. WHEN splitting text into Chunks, THE Tool SHALL split at the nearest sentence boundary (period, exclamation mark, or question mark followed by whitespace) at or before the 3,000-word limit; IF no sentence boundary exists within the last 100 words of a 3,000-word window, THE Tool SHALL split at exactly 3,000 words.
3. WHEN a Document's extracted text contains 3,000 words or fewer, THE Tool SHALL treat the entire text as a single Chunk and SHALL NOT apply overlap.
4. WHEN a Document produces more than one Chunk, THE Tool SHALL prepend the last 200 words of the preceding Chunk to the beginning of each subsequent Chunk to form the overlapping context.
5. IF a Document's extracted text contains zero words (empty or whitespace-only), THEN THE Tool SHALL log a warning identifying the file path, produce zero Chunks for that Document, and continue processing remaining documents.

---

### Requirement 5: QA Pair Generation via Claude API

**User Story:** As a user, I want the tool to send each chunk to Claude and receive structured Q&A pairs, so that the document content is converted into a useful FAQ format.

#### Acceptance Criteria

1. WHEN a Chunk is ready for processing, THE Tool SHALL send a request to the Claude_API using the `claude-sonnet-4-5` model, including the Chunk text and a prompt instructing the model to generate between 3 and 10 QA_Pairs.
2. THE Tool SHALL request that the Claude_API return QA_Pairs in a structured format where each QA_Pair is a discrete entry containing a non-empty question field and a non-empty answer field.
3. WHEN the Claude_API returns a successful response, THE Tool SHALL parse the response and extract all QA_Pairs where both the question and answer fields are non-empty; malformed or incomplete entries SHALL be discarded.
4. IF the Claude_API returns a rate-limit error (HTTP 429), THEN THE Tool SHALL wait 10 seconds and retry the request up to 3 times before logging an error and skipping the Chunk.
5. IF the Claude_API returns any other non-recoverable error, or if the response cannot be parsed, THEN THE Tool SHALL log the error with the Chunk identifier and continue processing remaining Chunks.
6. IF fewer than 3 valid QA_Pairs are extracted from a Chunk after parsing, THEN THE Tool SHALL log a warning identifying the Chunk and the count of pairs extracted, then continue processing remaining Chunks.

---

### Requirement 6: Merging QA Pairs

**User Story:** As a user, I want all Q&A pairs from all chunks and documents merged into one coherent FAQ, so that the output reflects the entire document set.

#### Acceptance Criteria

1. WHEN all Chunks have been processed, THE Merger SHALL collect all QA_Pairs from every Chunk across all Documents into a single list.
2. THE Merger SHALL preserve the question and answer text of each QA_Pair without modification during merging.
3. THE Merger SHALL order the merged list by Document name (alphabetical by full file path) and then by ascending Chunk index (0-based position within that Document) within each Document.

---

### Requirement 7: Deduplication of Questions

**User Story:** As a user, I want overlapping or duplicate questions removed from the FAQ, so that the output is concise and avoids repetition.

#### Acceptance Criteria

1. THE Deduplicator SHALL identify QA_Pairs whose questions are identical after applying lowercasing and collapsing all whitespace runs to a single space, and retain only the first occurrence in merge order.
2. THE Deduplicator SHALL compute TF-IDF cosine similarity between all remaining questions after exact-match deduplication, and for any cluster of questions with pairwise similarity above 0.85, retain only the QA_Pair with the longest combined question-plus-answer character count.
3. WHEN deduplication removes one or more QA_Pairs, THE Tool SHALL print to standard output the message `Removed N duplicate(s)` where N is the count of removed pairs.
4. THE Deduplicator SHALL ensure at least one QA_Pair per Document is present in the final FAQ; IF all QA_Pairs from a Document were removed as duplicates, THE Deduplicator SHALL restore the QA_Pair with the longest combined question-plus-answer character count from that Document.

---

### Requirement 8: Output File Generation

**User Story:** As a user, I want the final FAQ saved as a Markdown file at `output/faq.md`, so that it is easy to read and share.

#### Acceptance Criteria

1. THE Tool SHALL write the final deduplicated FAQ to the file at the path `output/faq.md` relative to the current working directory.
2. WHEN the `output/` directory does not exist, THE Tool SHALL create it (including any missing parent directories) before writing the Output_File.
3. THE Tool SHALL begin the Output_File with a level-one Markdown heading: `# FAQ`.
4. THE Tool SHALL group QA_Pairs by their originating Document, with each group preceded by a level-three Markdown heading (`###`) containing the Document's file name (basename only, not the full path).
5. THE Tool SHALL format each QA_Pair as a level-two Markdown heading (`##`) containing the question, immediately followed by a paragraph containing the answer.
6. WHEN the Output_File already exists, THE Tool SHALL overwrite it with the newly generated FAQ without prompting.
7. IF the Output_File cannot be written due to a file system error, THE Tool SHALL print an error message identifying the output path and the reason, and exit with a non-zero exit code.

---

### Requirement 9: Progress Reporting

**User Story:** As a user, I want to see progress in the terminal while the tool runs, so that I know the tool is working and can estimate completion time.

#### Acceptance Criteria

1. WHEN the Tool begins processing a Document, THE Tool SHALL print to standard output: `Processing: <filename>` where `<filename>` is the basename of the Document.
2. WHEN the Tool completes processing a Chunk, THE Tool SHALL print to standard output: `  Chunk <i>/<n> done` where `<i>` is the 1-based chunk index and `<n>` is the total chunk count for the current Document.
3. WHEN the Output_File has been written, THE Tool SHALL print a final summary to standard output in the following format:
   ```
   Done.
   Documents processed: <N>
   QA pairs generated:  <N>
   Duplicates removed:  <N>
   Output:              output/faq.md
   ```
